# Step 03. 모델에게 어떤 정보를 어떻게 보여줬는가?

## 어떤 문제가 있었는가

결정적인 최근 행동과 실행 결과가 긴 History 뒤쪽에 놓이면 최대 토큰 길이에서 잘릴 수 있었습니다. 반대로 메타정보를 무작정 추가하면 중요한 Prompt가 희석됐습니다.

## 왜 이 방법을 선택했는가

모델 크기를 키우기 전에 같은 데이터의 표현을 개선하는 것이 비용이 낮고, 다음 행동은 최근 상태에 크게 좌우될 것이라는 가설을 세웠습니다.

## 어떻게 적용했는가

- v3: Prompt, 최근 Action 이름, 메타데이터, 전체 History를 직렬화했습니다.
- v3b: 직전 두 Action의 이름·인자·결과와 `[STATE]`를 앞에 배치했습니다.
- Args와 Result 길이에 예산을 두어 긴 내용이 입력 전체를 차지하지 않게 했습니다.
- Current Prompt를 앞쪽으로 이동하는 실험을 수행했습니다.
- Action 이름을 special token으로 압축한 구조 표현을 시험했습니다.
- Previous Action, Open Files, Git Dirty, CI Status 등의 메타피처를 개별적으로 검토했습니다.

## 결과가 어땠는가

모든 Feature가 단일 성능을 높이지는 않았습니다. v3b와 struct 표현은 단일 점수만 보면 항상 최고가 아니었지만 기존 모델과 다른 오류를 만들어 최종 Ensemble에 기여했습니다. 메타피처를 32차원으로 크게 확장한 27차는 Macro-F1 `0.7351`로 하락했습니다.

## 왜 성공하거나 실패했는가

최근 정보를 앞에 배치한 방식은 truncation 위험을 줄였습니다. 반면 약한 메타정보를 대량으로 추가하면 노이즈와 복잡성이 증가했습니다. Special token은 Teacher의 지도와 결합할 때는 유용했지만 CE 단독 결합 모델은 `0.7346`으로 실패했습니다.

## 다음에는 어떻게 활용할 것인가

Feature는 개수가 아니라 정보의 시점, 신뢰도, 토큰 예산으로 평가합니다. 단일 성능과 Ensemble 다양성 기여를 별도 지표로 관리하고, 각 Feature는 ablation으로 검증합니다.
