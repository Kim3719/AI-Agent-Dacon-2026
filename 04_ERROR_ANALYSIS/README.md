# Step 04. 모델은 어디에서, 왜 틀렸는가?

## 어떤 문제가 있었는가

전체 점수가 상승해도 네 개의 파일 탐색 행동 사이의 혼동이 반복되었습니다. 특히 `read_file ↔ grep_search` 혼동과 `list_directory` 과잉 예측이 컸습니다.

## 왜 이 분석을 선택했는가

Backbone을 키울지, 구조 Feature를 추가할지, 라벨 노이즈를 다룰지는 오류의 원인에 따라 달라집니다. 따라서 새 모델을 학습하기 전에 오류가 “몰라서 틀린 것인지, 알지만 순위가 뒤집힌 것인지, 데이터 자체가 모호한지” 구분하려 했습니다.

## 어떻게 적용했는가

- Confusion Matrix와 클래스별 F1을 확인했습니다.
- Step 위치, History 길이, 신뢰도, Top-1/Top-2 margin으로 오류를 나눴습니다.
- Oracle top-k에 정답이 포함되는 비율을 확인했습니다.
- Prompt-only 신호와 이전 Action 조건부 분포를 비교했습니다.
- Attention과 Integrated Gradients를 보조 분석으로 사용했습니다.
- `errors_all.csv`에 정답, 예측, top-3 확률, 입력 길이와 메타정보를 저장했습니다.

## 결과가 어땠는가

Oracle 분석에서 정답이 top-2와 top-3에 자주 포함됐지만 1순위가 뒤집히는 경우가 많았습니다. Cluster1 표본 중 margin `<0.3` 구간은 정확도가 무작위 4분류에 가까웠습니다. 단순 Feature 추가와 복잡한 구조는 이 문제를 안정적으로 해결하지 못했습니다.

## 왜 성공하거나 실패했는가

오류 분석 자체는 성공했습니다. 취약 클래스 문제가 단순한 Backbone 용량 부족만은 아니며, 관측 정보만으로 경계가 모호한 표본이 있음을 보여줬습니다. 다만 Attention은 모델이 실제로 그 토큰 때문에 판단했다는 증거가 아니므로 설명으로 과대해석하지 않았습니다.

## 다음에는 어떻게 활용할 것인가

후속 연구에서는 annotator agreement, 라벨 정의 검토, uncertainty calibration, noise-aware loss를 함께 사용합니다. “라벨 노이즈가 확정됐다”가 아니라 현재 분석에서 관찰된 강한 가능성으로 표현합니다.
