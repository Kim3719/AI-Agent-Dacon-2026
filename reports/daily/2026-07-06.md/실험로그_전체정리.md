## 1. 모델 개발 히스토리

| 모델 | 구성 | val Macro-F1 | 비고 |
|---|---|---|---|
| v1 | klue-roberta | 0.406 | 베이스라인 |
| v2 | xlm-roberta-base + Focal Loss | 0.633 | 리더보드 0.636 |
| **v3** | xlm-r-base, **입력 재설계** | **0.740** | 리더보드 0.7412. **가장 큰 도약(+0.11)** |
| v4 | v3 + 세션 행동횟수(CNT) 텍스트피처 | 0.738 | 실패 (트랜스포머엔 무효) |
| mDeBERTa v1 | mDeBERTa-v3-base, LR=1e-5, 6ep | 0.692 | LR 너무 낮음 |
| mDeBERTa v2 | 위 + LR=2e-5, 8ep | 0.727 | 재학습으로 개선, 그러나 앙상블 기여 미미 |
| xlm-r-large | v3 구성 + large 체급 | 0.725 | 체급 키워도 검색/읽기 혼동 그대로. **실패** |
| **v5** | v3 + 세션 43차원 수치피처(팀원식 concat) | 0.730 | 단독은 낮지만 앙상블에 미세 기여(+0.001, 검증됨) |
| v3 fold0~4 | v3 구성, StratifiedKFold 5분할 | 0.715~0.769(val), OOF 0.72 | ⚠️ **val 점수에 누수 있었음** (아래 8번 참고) |

**v3 입력 재설계 (핵심 도약, v2→v3 +0.11)**
```
[PROMPT] {current_prompt} [LAST] {직전행동3개} [META] {세션메타} [HIST] {history 역순}
```
v2는 truncation으로 28% 샘플의 current_prompt가 잘렸음. 중요 정보를 앞으로 재배치해서 해결.

**팀원 모델 (mate)**: TextMetaClassifier 구조 (xlm-r backbone + turn_index 수치 concat). val 0.773, 리더보드 0.74 (val 과대평가 확인됨).

## 2. 앙상블 시도 전체

| 조합 | val | 리더보드 | 판정 |
|---|---|---|---|
| mate + v3 (int8, our=0.7) | 0.776 | **0.7574** | 팀 최고 갱신 |
| mate + v3 + mDeBERTa (3-way) | 0.7779 | 미제출 | mDeBERTa 기여 +0.0006, 무의미 |
| 5개 모델(v3,v4,mdeb,large,mate) 전체 최적 | 0.7786 | — | **split검증 시 과최적화 확인** (단순조합보다 못함) |
| mate + v3 + v5 (+배수튜닝) | 0.784(h2) | **0.7588** | 팀 최고 갱신, val↔리더보드 예측 정확히 일치 |
| mate + fold0 + fold1 | 0.7797(h2) | **0.7520** | ❌ **fold 누수로 실패**, 최고 기록 아님 |

**과최적화 진단 방법 (split validation)**: val 7000개를 h1/h2로 반씩 나눠, h1에서 가중치 튜닝 → h2에서 검증. h2에서도 오르면 진짜, 아니면 val 과최적화.

## 3. 오답 분석 & 핵심 발견

### 3-1. 정밀 오답분석 (5개 모델 val 예측/확률 기반)
- **3모델 공통 오답 1240개(전체의 17.7%)** 분석 → 74%가 검색/읽기 4개(read/grep/list/glob)에 집중
- 세 모델(다른 구조)이 **똑같은 Top 혼동 쌍**을 보임 → 모델 문제 아니라 데이터 문제
- 검색/읽기 오답의 **100%가 자기들끼리만 혼동** (다른 범주와 절대 안 섞임) → 문제가 국소화됨
- 오답의 85%는 "정답이 확률 2~3등" (근소한 차이, 완전 무작위 아님)

### 3-2. ★ 라벨 노이즈 확정 ★ (여러 각도로 검증)
- 실제 오답 프롬프트 확인: "grep the whole thing" → 정답 read_file, "검색해줘" → 정답 read_file 등 **명백한 라벨 오류 다수**
- **prompt 키워드로 4개 클래스가 전혀 안 갈림** (전체 70000개 통계: "검색해줘/찾아줘" 있어도 없어도 grep 비율 동일)
- 전문가 4-클래스 분류기 프록시 실험: F1 0.49 (현재 앙상블 0.62보다 **낮음**) → 4개만 떼어놔도 안 풀림
- open_files 유무: list_directory 비율만 6%→26%로 갈림(약한 신호), read vs grep은 여전히 안 갈림
- prompt-history cross reference(대상이 이미 언급됐는지): 효과 없음
- **결론: read/grep/list/glob 4개는 입력만으로 예측 불가능한 라벨 노이즈. 어떤 모델·피처로도 개선 안 됨.**

### 3-3. 개선 가능 영역 정량화 (클래스별 F1 완벽화 시 Macro 상승분)
| 클래스 | 현재 F1 | 완벽시 상승분 |
|---|---|---|
| list_directory | 0.504 | +0.035 |
| read_file | 0.615 | +0.028 |
| grep_search | 0.644 | +0.025 |
| web_search | 0.645 | +0.025 |
| glob_pattern | 0.700 | +0.022 |
| lint_or_typecheck | 0.712 | +0.021 |
| plan_task | 0.717 | +0.020 |

→ 검색/읽기(라벨노이즈, 못 고침) 외에 **web_search, lint, plan_task**는 개선 여지 있을 수 있음 (미착수).

## 4. 실패한 시도들 (교훈 — 시간 아끼는 용도)

| 시도 | 결과 | 이유 |
|---|---|---|
| v4: 세션 행동횟수(CNT) 텍스트 피처 | val 0.738 (v3와 동일) | 트랜스포머는 history를 이미 봐서, 파생 피처를 텍스트로 명시해도 새 정보 아님 |
| v5: 43차원 세션피처 수치 concat | 단독 0.730 (v3보다 낮음) | 위와 동일 이유. 앙상블에선 +0.001 미세 기여(검증됨) |
| xlm-r-large 체급 업 | val 0.725 (base보다 낮음) | 체급 키워도 라벨노이즈는 안 풀림. 5ep로 덜 학습됐을 가능성도 |
| 검색/읽기 샘플 다운웨이트 재학습 | 전체 -0.01 | 노이즈만 골라 못 빼고 유효신호까지 같이 죽임 |
| 로지스틱 앙상블 얹기 | h2 +0.0002 | mate+v3가 이미 강해서 약한 모델 얹어도 무의미 |
| **model soup (5-fold 가중치 평균)** | val 0.700 (fold평균 0.768보다 -0.068) | fold들이 손실지형의 다른 지점에 있어 평균내면 나쁜 지점에 안착 |
| **5-fold val 검증 → 제출** | val h2 0.7797 → 리더보드 0.7520 | **fold 분할과 평가 val 인덱스가 겹쳐서 누수.** OOF(0.72)가 진실에 가까웠음 |
| 3-way 이상 복잡한 앙상블 가중치 정교화 | val 오름, h2 검증시 단순조합보다 못함 | 과최적화 |

## 6. 핵심 방법론 교훈

1. **val ≠ 리더보드.** 특히 다른 사람 모델은 val 과대평가 가능성 있음 (mate: val 0.773 → 리더보드 0.74). 반드시 리더보드 실측 또는 **split validation**(val을 h1/h2로 나눠 교차검증)으로 확인.

2. **fold 분할 시 누수 주의.** 평가용 val(train_test_split)과 K-fold 분할이 겹치면, fold의 val 성능이 뻥튀기됨. **OOF 점수가 val 점수보다 훨씬 낮으면 누수 경고 신호.** 이번에 OOF 0.72 vs val 0.769 차이를 놓쳐서 제출 실패함.

3. **트랜스포머는 이미 history를 본다.** history에서 계산 가능한 파생 피처(행동 횟수, 비율 등)를 텍스트나 수치로 다시 줘도 효과 없음. **잘려서 안 보이던 정보를 살리는 것**(v3의 truncation 수정)만 확실히 먹힘.

4. **model soup은 리스크 있음.** 여러 fine-tuned 모델의 가중치를 단순 평균하면 오히려 성능이 크게 떨어질 수 있음. 확률(logit) 앙상블이 안전.

5. **앙상블 다양성은 아키텍처가 아니라 입력/구조 차이에서 옴.** mDeBERTa(다른 아키텍처)는 입력이 같아서 앙상블 기여 거의 없었지만, mate(다른 입력구조: 수치 concat)는 확실히 기여함.

6. **복잡한 다중모델 앙상블은 과최적화되기 쉬움.** 항상 split validation으로 단순 조합과 비교할 것.

## 7. 현재 결론 및 팀 제안

- **검색/읽기 4개 클래스는 라벨 노이즈로 확정.** 여기 시간 쓰지 말 것. (증거: common_errors.csv, 프록시 실험들)
- **개인 앙상블(mate+v3+v5)은 0.7588에서 천장.** 추가 모델(large, mdeb, fold soup) 다 시도했지만 유의미한 개선 없음.
- **팀 앙상블이 다음 승부처일 가능성.** 서로 다른 사람이 서로 다른 구조로 만든 모델들을 모으면, 개인이 못 넘은 천장을 넘을 수 있음. 각자 모델의 val 확률(logits)을 공유해서 팀 전체 앙상블 조합을 찾는 걸 제안.
- **주의사항 공유**: fold/기법 실험 시 val 누수 체크, val≠리더보드 항상 split 검증.
