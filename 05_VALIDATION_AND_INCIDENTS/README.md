# Step 05. 높은 Validation 점수를 정말 믿을 수 있는가?

## 어떤 문제가 있었는가

로컬 점수 상승이 Public 성능으로 이어지지 않았고, Validation `0.774` 수준으로 평가된 제출이 Public `0.6619`를 기록한 큰 실패도 있었습니다. Threshold와 가중치 조정은 한 Split에서는 좋아 보였지만 반복 검증에서 뒤집혔습니다.

## 왜 검증 방식을 바꿨는가

같은 세션의 여러 Step은 서로 독립적이지 않습니다. 같은 세션이 Train과 Validation에 동시에 포함되면 모델이 세션 고유 정보를 활용해 실제보다 좋아 보일 수 있었습니다.

## 어떻게 적용했는가

- 세션 단위 GroupKFold를 도입했습니다.
- Random split과 Group split이 모두 개선될 때만 후보를 채택했습니다.
- 작은 향상은 여러 번 반복해 평균과 변동성을 확인했습니다.
- 저장 예측과 재생성 예측의 argmax 일치율로 모델·입력 정합성을 확인했습니다.
- 학습과 제출이 동일한 입력 함수를 사용하도록 점검했습니다.
- Checkpoint, 확률, Config를 분리해 보존하는 원칙을 세웠습니다.

## 결과가 어땠는가

- Per-class offset은 5회 반복 평균 `-0.0007 ± 0.0042`로 기각했습니다.
- Seed 가중치 조정은 단순 평균 대비 약 `-0.0010`으로 기각했습니다.
- Public `0.6619` 사고는 저장 모델 덮어쓰기와 학습·제출 입력 불일치를 조사하는 계기가 됐습니다.
- Group 기반 검증은 이후 Teacher와 후처리 후보의 가짜 개선을 걸러내는 기준이 됐습니다.

## 왜 성공하거나 실패했는가

단일 Validation을 반복해서 튜닝하면 심판 역할을 잃습니다. 또한 좋은 모델이라도 추론 시 다른 입력을 받으면 전혀 다른 시스템입니다. 문제는 모델 구조가 아니라 평가와 운영 파이프라인 전체에 있었습니다.
